# 測試計畫（TDD 導向）

## 核心原則

> **一次只為一個 SDD Issue 建立對應的 TDD，測試案例保持最小化，並明確告訴使用者「下一步做什麼」**

## 目的

將 SDD 的技術規格轉換為具體的測試計畫，但保持「單一任務」的專注度，避免一次產出過多測試案例。

---

## Phase 1：讀取 SDD Issue

### Step 1.1：取得 SDD 內容

1. 透過 MCP 讀取指定的 SDD Issue
2. 確認 SDD Issue 已建立完成
3. 提取關鍵資訊：
   - 任務 ID
   - 技術規格（介面、輸入/輸出、錯誤處理）
   - 對應的 BDD Scenarios

### Step 1.2：檢查前置條件

```
⚠️ 若 SDD Issue 未完成，停止並提醒：
「請先完成 SDD Issue #YY 後再繼續」
```

---

## Phase 2：測試計畫（最小化版）

### Step 2.1：識別核心測試場景

只關注**最重要**的測試場景（最多 5 個）：

```
① 成功路徑（Happy Path）- 必須
② 主要失敗路徑 - 必須
③ 邊界條件 - 視情況
④ 異常處理 - 視情況
```

### Step 2.2：快速確認問題

只問**必要**的測試問題（最多 2-3 題）：

```
① 這個功能最重要的測試場景是什麼？
   A) 成功建立/取得/更新/刪除
   B) 驗證失敗
   C) 權限不足
   D) 其他（請說明）

② 測試需要什麼 Mock？
   A) 不需要
   B) 資料庫 Mock
   C) 外部 API Mock
   D) 其他（請說明）
```

### Step 2.3：產出精簡測試矩陣

**測試矩陣格式（精簡版）：**

```markdown
## 測試矩陣

| # | 測試名稱 | 類型 | 輸入 | 預期結果 | 優先級 |
|---|----------|------|------|----------|--------|
| 1 | 成功路徑 | Unit | [簡述] | [簡述] | P0 |
| 2 | 驗證失敗 | Unit | [簡述] | [簡述] | P0 |
| 3 | [其他] | Unit | [簡述] | [簡述] | P1 |

> 💡 測試案例數量限制：最多 5 個。若超過，請拆分成多個任務。
```

---

## Phase 3：建立 TDD Issue

### Step 3.1：產出 TDD Issue

**TDD Issue 格式（精簡版）：**

```markdown
## Issue 標題
`TDD-TASK-001 - [測試主題]`

## 對應 Issue
- BDD Issue: #XX
- SDD Issue: #YY
- 任務 ID: TASK-001

## 測試矩陣
| # | 測試名稱 | 類型 | 預期結果 | 優先級 |
|---|----------|------|----------|--------|
| 1 | ... | ... | ... | ... |

## 測試環境需求
- [ ] Mock 設定：[說明]
- [ ] 測試資料：[說明]

## 完成定義
- [ ] 所有 P0 測試通過
- [ ] 測試覆蓋率 > 80%
```

### Step 3.2：建立 Issue 與關聯

1. 透過 MCP / GitHub API 建立 TDD Issue
2. 將 TDD Issue 設為 SDD Issue 的 Sub-Issue

---

## Phase 4：明確的下一步指令

### 輸出模板

每次回覆結尾**必須**包含：

```markdown
---

## ✅ 本次完成
- 建立了 TDD Issue: `TDD-TASK-001 - [主題]` (#Issue編號)
- 已關聯至 SDD Issue #YY

## 🎯 下一步
執行 `@workspace /tdd-red.prompt.md` 並提供：
- TDD Issue 編號：#ZZ
- 任務 ID：TASK-001
- 第一個要寫的測試：測試 #1 - [測試名稱]

## 📋 目前任務狀態
| 任務 ID | BDD | SDD | TDD | 狀態 |
|---------|-----|-----|-----|------|
| TASK-001 | #XX | #YY | #ZZ | 🔴 準備寫第一個測試 |
| TASK-002 | - | - | - | ⏸️ 等待 TASK-001 |

---
```

---

## 禁止事項

❌ **禁止**一次處理多個 SDD Issue
❌ **禁止**產出超過 5 個測試案例（超過就拆分任務）
❌ **禁止**沒有明確「下一步」就結束回覆
❌ **禁止**寫出過於複雜的測試計畫

---

## TDD 循環狀態

| 狀態 | 符號 | 說明 |
|------|------|------|
| 準備測試 | 📋 TDD | TDD Issue 已建立 |
| Red 階段 | 🔴 Red | 正在寫失敗測試 |
| Green 階段 | 🟢 Green | 正在實作通過測試 |
| Refactor 階段 | ♻️ Refactor | 正在重構 |
| 完成 | ✅ Done | 測試全部通過 |

---

## 範例輸出

```markdown
## ✅ 本次完成
- 建立了 TDD Issue: `TDD-TASK-001 - Email 登入測試` (#15)
- 測試矩陣包含 3 個測試案例

## 🎯 下一步
執行 `@workspace /tdd-red.prompt.md` 並提供：
- TDD Issue 編號：#15
- 任務 ID：TASK-001
- 第一個要寫的測試：測試 #1 - 成功登入應回傳 JWT Token

## 📋 測試進度
| # | 測試名稱 | 狀態 |
|---|----------|------|
| 1 | 成功登入應回傳 JWT Token | 🔜 下一個 |
| 2 | Email 格式錯誤應回傳 400 | ⏸️ |
| 3 | 密碼錯誤應回傳 401 | ⏸️ |
```

1. 根據 Step 2 的對話結果與 BDD Issue 中的功能 ID，為每個測試場景建立「Test ID」
   - 格式：`{功能ID}-T-{序號}`（例如 REQ-001-T-101、REQ-001-T-102）
   - 這樣可以確保每個功能的測試編號唯一，避免跨功能重複
   - 對應 BDD 的 `US<序號>-S<序號>` Scenario ID
