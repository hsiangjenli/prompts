# 需求變更管理（BDD/SDD/TDD 中途修正）

## 目的

當專案在 BDD、SDD 或 TDD 階段進行中時發現需要新增或修改需求，協助快速：
1. 評估變更對既有 Issue 與設計文件的影響
2. 確定需要回溯哪一層級進行調整
3. 更新所有受影響的 GitHub Issue，避免文件不一致
4. 於 BDD Issue 建立變更追蹤 Comment，提供完整審計軌跡

## 重要原則

- **模板優先**：所有 ID 格式、欄位名稱、命名規則皆以 `markdown-template` 工具回傳的模板為準，本 Prompt 不定義具體格式
- **逐層確認**：每更新一個 Issue 後，必須向使用者確認內容無誤，才進行下一層級
- **完整追蹤**：所有層級更新完成後，於 BDD Issue 建立變更追蹤 Comment

## 前置條件

- 至少已有一個已建立的 BDD Issue（即使尚未核准）
- 能清楚說明變更的背景、觸發點（BDD/SDD/TDD 哪個階段發現）
- 對現有的 Issue 狀態、相關 PR/分支有基本了解

## 何時啟動此 Prompt

- **BDD 階段**：發現需要新增 User Story 或調整 Scenario
- **SDD 階段**：發現設計缺漏或規格需要調整（需回溯至 BDD 驗證）
- **TDD 階段**：測試執行時發現邏輯或驗收條件有誤（需回溯至 SDD 更新設計）
- **實作中**：程式碼實作時才發現需求不清或設計不足（需全面評估影響）

## 提問原則

- 採「單一問題 + 選項 + 自訂輸入」格式，便於快速判定
- 每題最多 4 個選項，預留「其他／自行輸入」選項
- 一次只問一個問題，避免資訊過載

### 常用問題題庫

```
- 變更來自哪個階段的發現？
  ① BDD（需求本身不清）  ② SDD（設計有誤）  ③ TDD（測試無法進行）  ④ 其他（請說明）

- 這個變更是否影響現有的 User Story 或 Scenario？
  ① 新增新的 Scenario  ② 修改既有 Scenario  ③ 刪除某個 Scenario  ④ 其他（請說明）

- 是否需要調整系統設計或規格？
  ① 需要修改 API 介面  ② 需要新增資料欄位  ③ 需要調整驗證邏輯  ④ 其他（請說明）

- 變更是否影響已建立的 TDD 測試計畫？
  ① 需要新增測試場景  ② 需要修改測試場景  ③ 需要刪除測試場景  ④ 其他（請說明）

- 這個變更的優先順序是多少？
  ① P0（立即進行，阻塞當前工作）  ② P1（本週內完成）  ③ P2（可延後）  ④ 其他（請說明）

- 變更是否影響非功能需求或部署流程？
  ① 需要調整 CI/CD  ② 需要新增監控  ③ 不影響  ④ 其他（請說明）

- 您期望如何同步此變更？
  ① 直接更新相關 GitHub Issue  ② 產出變更摘要由我手動貼上  ③ 兩者都要  ④ 其他（請說明）
```

## 操作流程

### Step 1：判定變更層級與更新順序

1. **詢問變更來自何處**
   - 是在 BDD（需求層面）、SDD（設計層面）還是 TDD（測試層面）發現？
   - 根據發現位置決定更新順序：
     - **在 BDD 發現**：BDD → SDD → TDD（順向更新）
     - **在 SDD 發現**：先回溯 BDD 驗證 → 再更新 SDD → TDD
     - **在 TDD 發現**：全面回溯 BDD、SDD 驗證 → 依序更新 SDD → TDD

2. **確認現有 Issue 狀態**
   - 使用 `mcp_github_issue_read` 讀取相關的 BDD/SDD/TDD Issue
   - 檢查是否存在相關的 PR、分支或已實作程式碼
   - 確認受影響的 Scenario ID

### Step 2：評估變更影響

1. **逐層分析影響**
   - **BDD 層**：哪些 User Story 或 Scenario 受影響？需新增、修改還是刪除？
   - **SDD 層**：相應的設計、契約、資料模型是否需要調整？
   - **TDD 層**：測試矩陣、測試場景、驗收條件是否需要更新？

2. **蒐集必要資訊**
   - 若資訊不足，透過問答補齊（使用「常用問題題庫」）
   - 標記待確認項目為「待確認」或「需人工決策」

3. **整理影響範圍清單**
   - 記錄各層級受影響的項目（供 Step 5 建立 Comment 使用）

### Step 3：建立變更方案

1. **整理變更清單**
   - 使用 Markdown 表格整理所有受影響的項目，供使用者總覽
   - 表格應包含：層級、Issue 編號（或「新建」）、受影響項目、變更類型

2. **建立待辦任務**
   - 呼叫 `todos` MCP 工具，依 Step 1 決定的更新順序建立任務
   - 每個待更新或新建的 Issue 建立一個獨立任務
   - 任務描述應包含：層級、Issue 編號、變更內容摘要

3. **向使用者確認變更方案**
   - 展示變更清單表格與待辦任務
   - 詢問：「以上變更方案是否正確？確認後將依序執行各任務。」
   - 若使用者有異議，調整方案並更新 `todos` 後重新確認
   - 只有在使用者確認後，才進入 Step 4 執行更新

### Step 4：執行同步（逐層更新 + 確認）

**重要**：依 `todos` 任務順序逐一執行，每完成一個任務後標記完成並要求使用者確認。

1. **執行當前任務**
   - 從 `todos` 取得下一個待執行任務
   - 呼叫 `markdown-template` 工具取得對應模板（BDD/SDD/TDD）
   - 依模板格式更新或建立 Issue
   - 使用 `mcp_github_issue_write` 執行更新
   - 生成更新摘要，清晰展示新增/修改的內容

2. **確認並標記完成**
   - **要求使用者確認**：「以上 Issue #X 的變更內容是否正確？」
   - 使用者確認後，呼叫 `todos` 標記該任務為完成
   - 若使用者要求修正，調整後重新確認

3. **重複直到所有任務完成**
   - 依序執行 `todos` 中的所有任務
   - 每個任務都需經使用者確認後才標記完成並進入下一個

4. **確保 Sub-Issue 關聯一致**
   - 所有任務完成後，檢查三層 Issue 之間的 Sub-Issue 關聯是否正確
   - 若有新建 Issue，確保已建立正確的 Sub-Issue 關聯

### Step 5：建立變更追蹤 Comment

**時機**：所有層級 Issue 更新完成並經使用者確認後執行。

1. **取得 Comment 模板**
   - 呼叫 `markdown-template` 工具取得 `change-comment` 模板
   - 確認模板要求的所有欄位

2. **填入模板欄位**
   - 依模板要求填入所有欄位
   - 欄位內容來源：
     - 變更發現層級（來自 Step 1）
     - 變更背景與原因（來自 Step 2 問答蒐集）
     - 影響範圍清單（來自 Step 2 分析結果）
     - 受影響的 Issue 編號（來自 Step 4 更新紀錄）

3. **於 BDD Issue 建立 Comment**
   - 使用 GitHub API 在對應的 BDD Issue 中建立新 Comment
   - 若無權限，輸出完整 Comment 內容供使用者手動貼上

### Step 6：輸出摘要與後續行動

1. **輸出變更確認表**
   - 列出所有已更新的 Issue（編號與連結）
   - 列出已建立的變更追蹤 Comment 連結
   - 列出待人工確認的項目

2. **後續行動指引**
   - 若 BDD 有調整，可能需執行 `requirements.prompt.md` 補充細節
   - 若 SDD 有調整，可能需執行 `sdd.prompt.md` 補充設計
   - 若 TDD 有調整，可能需執行 `tdd-requirements.prompt.md` 更新測試計畫

## 注意事項

- **不自行決策**：若資訊不足，直接向使用者追問；不得自行猜測變更內容
- **格式依模板**：所有 ID、欄位名稱、表格結構皆以 `markdown-template` 回傳為準
- **完整追蹤**：引用 GitHub Issue 時一律使用 `#編號` 格式
- **待確認標註**：對於推測或需確認的項目，標註「待確認」或「需決策」
- **避免重複**：變更同步後，檢查是否產生重複或衝突的 Scenario/測試項
- **Comment 時機**：變更追蹤 Comment 必須在所有 Issue 更新完成後才建立，確保記錄完整

## 錯誤處理

| 情況 | 處理方式 |
| --- | --- |
| 找不到指定的 BDD/SDD/TDD Issue | 提示使用者確認 Issue 編號是否正確 |
| `markdown-template` 無法取得模板 | 提示使用者確認 MCP 工具是否正常運作，暫停流程 |
| 使用者未確認即要求進行下一層更新 | 拒絕進行，重新要求確認當前層級的變更 |
| GitHub API 權限不足 | 輸出完整 Markdown 草稿，指導使用者手動更新 |
| 變更影響範圍無法判定 | 列出可能的影響範圍，標記為「待確認」，要求使用者協助釐清 |
| Comment 建立失敗 | 輸出完整 Comment 內容，指導使用者手動於 BDD Issue 貼上 |
